# Project Overview: Issue-to-First-PR Mentor

## One-paragraph overview
The Issue-to-First-PR Mentor is a small Streamlit web app. A first-time open-source
contributor pastes a link to a public GitHub issue. The app reads the issue through the
public GitHub REST API, sends the issue text to Gemma 4 through the Gemini API, and shows a
beginner-friendly plan: what the issue asks for, how hard it is, which files to read first,
five numbered steps, and questions to ask the maintainer. The app exists to help a
beginner start contributing without getting lost, and to make open-source work less
intimidating for students in Faisalabad and similar communities.

## Problem statement
New contributors often fail to start open-source work for three reasons. They do not know
which files matter. They do not know whether an issue is already claimed or too advanced.
They freeze because the maintainer's language is terse. The app addresses the first and
third reasons directly and reports issue state, which partly addresses the second.

## Target user
A university student or early-career developer. They have a GitHub account and have written
some Python or other code. They have not yet made an accepted pull request to a project
they did not start. They may be more comfortable reading Urdu or English explanations than
dense technical English, but v1 is English-only.

## Goals (measurable)
- G1: For a valid public issue link, the app shows a complete plan with all five sections
  within 30 seconds in the demo environment. Measured by testing 5 real "good first issue"
  links and timing each.
- G2: Every plan generation call goes through the Gemini API using the Gemma 4 model name
  configured in GEMMA_MODEL. Measured by reading the code path and the model name in the
  request log entry.
- G3: No API key or token appears in the repository, the browser, logs, or the output.
  Measured by the secret scan steps in ai-workflow-rules.md.
- G4: The app runs live for the full 3-minute demo, including one deliberate error case
  (bad link), without a crash or a traceback shown to the user.
- G5: The repository is public, carries an MIT LICENSE, and its README names the model and
  links its license. Measured on the submission checklist.

## Core user flow
1. The user opens the app and sees a single text box labelled "GitHub issue URL".
2. The user pastes a link such as https://github.com/owner/repo/issues/123.
3. The user clicks "Build my plan".
4. The app checks the link format. If it is wrong, it shows a clear message and stops.
5. The app checks cooldown and the daily demo cap. If either blocks the request, it says so.
6. The app fetches the issue title, body and state from GitHub.
7. The app sends the issue text to Gemma and receives a plan.
8. The app shows the issue title, the state (open or closed), and the plan.
9. If anything fails, the user sees one plain-language error message and no technical detail.

## Features for v1 (in scope)
- Strict validation of GitHub issue links (github.com only, issue numbers only).
- Fetching a public issue's title, body and state through the GitHub REST API.
- Optional GITHUB_TOKEN for higher GitHub rate limits, using a token with no permissions.
- A five-section plan generated by Gemma 4 through the Gemini API.
- Plain-language error messages for: invalid link, pull request link, issue not found,
  GitHub unreachable, model failure, cooldown, and daily cap.
- Per-session cooldown of 15 seconds between plan requests.
- Process-wide daily cap on plan generation (default 100, set by DAILY_PLAN_CAP).
- Caching of fetched issue content for 10 minutes to reduce repeated GitHub calls.
- Configuration through environment variables loaded from a local .env file.

## Out of scope for v1 (do not build)
- User accounts, login, sign-up, or any personal profile.
- Any database, file storage, or saved plan history.
- Reading the repository file tree, README, CONTRIBUTING.md, or issue comments. These are the
  first stretch goals, after v1 is stable.
- Searching for "good first issue" issues across repositories.
- Writing or posting comments, opening pull requests, or taking any action on GitHub.
- Uploading files of any kind, including past papers. The past-paper feature was requested
  and explicitly declined for this project. It belongs to a separate app.
- Voice input, mobile apps, browser extensions, or Chrome integrations.
- Urdu user interface or Urdu output. This is a stretch goal only if the English demo works.
- Custom CSS, custom HTML components, or JavaScript in the app.
- Any agent behaviour: the model has no tools and cannot take actions.
- Accepting links from hosts other than github.com, including GitHub Enterprise and gist links.

## Stretch goals, in priority order (only after G1 to G5 pass)
1. Read the repo file tree and feed real file paths into the prompt.
2. Show whether the issue already has an assignee or a linked pull request.
3. Read CONTRIBUTING.md and include its rules in the plan.
4. A progress checklist for the five steps, kept in session state.
5. Draft a polite claiming comment that the user can copy and post themselves.

## Success criteria (verifiable)
- A valid public issue link returns all five plan sections on the first try in at least
  4 of 5 test runs with real issues.
- An invalid link returns a specific error message in under 1 second and makes no GitHub
  or Gemini call. Verified by watching the logs during the test.
- A private repository or a missing issue returns the "not found" message, not a traceback.
- The app has no code path that echoes an exception message to the browser.
- Every item in the security section of architecture.md has a verification note in
  SECURITY-AUDIT.md.
